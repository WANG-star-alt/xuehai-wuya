§ 5.1 · Section

选型地图：先想清楚要做什么

The Selection Map · Choose the Tool After You Know the Job

前四章是一场原理的远征：像素怎么画（第 2 章）、版面怎么摆（第 3 章）、点击背后发生了什么（第 4 章）。现在原理弹药带够了，第 5 章换挡，从「懂了」走向「做出来」。但动手写第一行代码之前，横着一个小白必栽的坑：工具选什么？Tkinter、PySide6、Streamlit、Electron、Tauri、Avalonia……名字比概念还多，论坛上人人都有自己的心头好，吵得不可开交。本节的论点只有一句话：先想清楚要做什么，再决定用什么做——顺序反了，就是拿着锤子满世界找钉子。这一节把整个桌面界面开发的世界画成一张地图：先教你用五个问题把「我想做个东西」翻译成清楚的需求，再把五大技术栈各自的看家本领和致命短板讲明白，最后给出一张决策树、一张对比总表、三类典型人群的答案卷。读完你未必立刻会写界面，但你一定知道自己该往哪条路走——选型选对了，后面五节的路程至少省一半力气。

生活场景
🧰 老陈不带徒弟去买那套德国工具

厂里干了三十年维修的老陈，工具间整整一面墙的家什。徒弟小林入职第一天就想刷一套德国进口的 108 件工具——「一步到位，省得以后再买」。老陈没接话，先问了一句：「你明天要干的第一个活是什么？」「给车间的配电柜换个螺丝。」「那你今天只需要一把十字螺丝刀，仓库领，不要钱。」

小林不服气。一个月跟下来，他发现自己腰带上只有五件家什——一把螺丝刀、一支电笔、一把尖嘴钳、一卷绝缘胶带、一支手电——但每一件都天天在用，那套想象中的 108 件从头到尾没派上过用场。老陈说：「工具是拿来干活的，不是拿来收藏的。先有活，后有工具。」

小林后来又发现一个细节：五金城从来不按品牌分区——没有「博世区」「得伟区」，只有「钻孔区」「水电区」「木工区」。你要打孔，就直奔钻区比较几款钻；而不是先决定「我这一生只用博世」，再琢磨拿它干点啥。第 5 章就是界面开发的五金城：六大节按「你要做什么」分区，不按框架品牌分区——而本节，是门口那张导购图。

选型为什么是第一课：先有活，后有工具

新手教程惯常的顺序是「先学工具，再做项目」：第一章装环境，第二章写 Hello World，第十章才轮到你想要的东西。这个顺序对学语言没问题，对选框架却是灾难——因为你连自己要做什么都没说清，凭什么决定用哪个工具？说白了，框架之争吵不出胜负的根本原因是：争论双方做的根本不是同一件事。做三天小工具的人说 Tkinter 真香，做工业软件的人说 Qt 才是正经路，写前端出身的人说 Electron 生态无敌——他们都没说错，因为他们手里的「活」不一样。

选错工具的代价分三层，一层比一层贵：学不会（工具与你的语言背景错位，入门就卡死）、做不完（工具的短板恰好撞在你的需求上，比如用纯 Tkinter 硬撑多窗口复杂交互）、养不起（东西做出来了，但打包 200MB、用户装不上、每次更新要重发）。第三层最隐蔽也最致命——它在你「做完」之后才发作。

所以本节的任务不是「告诉你哪个框架最好」——世界上没有最好的框架，只有最合适的框架——而是给你一套把需求翻译成技术条件的方法。翻译做完，答案往往是显然的；翻译没做，看再多对比文章也是越看越糊涂。打个比方：相亲不先想清楚自己要过什么日子，条件列表再长也挑不出人。

第一问：给谁用——受众决定一切成本

五个问题里，「给谁用」排在第一，因为它决定你后面所有成本的大小。受众分三档，一档比一档贵：

受众部署成本典型场景生活对照
只有自己零——装好环境就能跑，界面丑都无所谓批量改文件名、爬虫结果查看在家做饭，穿着围裙随便吃
同事 / 小圈子中——对方电脑可能没装 Python，得打包成 exe部门内部查库存、生成报表食堂做饭，得保证人人能吃
陌生公众高——安装包、代码签名、自动更新、多平台，一样不能少上架分发的正经产品开餐厅，消防卫生执照齐全

同一道菜，自家吃和开餐厅卖，要求天差地别：自家吃不用管卖相，餐厅要管食材溯源、出餐速度、顾客投诉。界面开发一模一样：给自己用，Tkinter 默认那副九十年代外观完全不影响；发给陌生用户，启动慢两秒、安装包大 100MB，都会被直接卸载。很多人选型翻车，就是用第一档的需求，操第三档的心——明明是给自己用的脚本加壳，却纠结「这个框架打包出来不够专业」。反过来也一样：要做正经产品，就不能只图「写起来快」。

判断受众还有个隐藏问题：用户的电脑环境你控制不了。同事的电脑可能是五年前的 Win7，陌生用户里有人用 4K 屏、有人用 13 寸笔记本——这些都会反过来影响选型（详见 § 5.6 打包与分发）。

第二问和第三问：要不要联网、你最顺手哪门语言

第二问：要不要联网、要不要多端？如果答案是「要」——比如希望手机上也能打开、或者界面要给别人远程看——那你的最佳路线大概率是 B/S 架构：程序在你电脑或服务器上跑，界面借浏览器显示。这样一来，Win/Mac/手机三端全通，用户什么都不用装，只要有个浏览器。Streamlit、Gradio、NiceGUI（§ 5.4）走的就是这条路，本质上就是「外卖模式」：厨房在你家，菜送到任何人的浏览器窗口。反过来，如果答案是「不要」——工具就该离线跑、数据不出本机——那就走 C/S 纯桌面路线，本节地图上的另外四个阵营。

第三问：你最顺手的语言是什么？这一问经常被新手忽略，却是杀伤力最大的一问。「学一门新语言 + 学一个新框架」双线作战，是新手翻车的头号原因。界面框架只是语言之上的皮：你顺 Python，那 Tkinter、PySide6、Streamlit 全在你的一亩三分地里；你是前端出身，Electron 和 Tauri 让你丝滑复用全部手艺；你写 C#，.NET 全家和 Avalonia 敞开大门。语言的语法、调试、生态你都要现学，再叠加一个框架的事件模型、布局系统——说白了，就是同时扛两座山。除非有硬理由，否则永远选你已有语言覆盖的路线：先会做东西，再谈换语言。

阵营一：Python 自带的瑞士军刀——Tkinter 与 CustomTkinter

Tkinter 的立身之本只有四个字：标准库自带。只要装了 Python，Tkinter 就躺在里面，一行 import 就能用，不装任何第三方包。它的底层是 Tcl/Tk——一套 1991 年就问世的老牌界面库，三十年风吹雨打，稳定得像块砖。用 Python 写小工具的人几乎都绕不开它：批量重命名、Excel 合并器、定时提醒、给爬虫脚本加个「开始/停止」按钮——这类「表单级」的小活，Tkinter 从想法到能跑，常常不超过一小时。

CustomTkinter 则是给这把军刀换了个刀柄：同一套控件、同一套写法，但换上现代化的圆角、深色模式、扁平外观——Tkinter 默认那张九十年代的脸，被它整容成了当代审美。学 Tkinter 的成本几乎原封不动地继承过来。

它的死穴也摆在明面上：复杂界面代码量爆炸。三五个输入框的小窗口是它的主场；一旦要多窗口嵌套、复杂列表、专业表格编辑，代码会以肉眼可见的速度失控——没有拖拽设计器，每个控件都要手写位置和样式。就像骑自行车去隔壁小区，方便；骑它去外地，就是自讨苦吃。给谁用、做多复杂的判断在这里立竿见影：自己用的小工具，它是命中注定的答案；正经产品，它撑不起门面。施工细节见 § 5.2。

体量有多小？一个能点按钮、弹提示框的完整窗口，六行搞定：

import tkinter as tk
from tkinter import messagebox

root = tk.Tk()                                # 主窗口
tk.Button(root, text='点我',
          command=lambda: messagebox.showinfo('你好', '就这么快')).pack()
root.mainloop()                               # 事件循环：窗口的发动机

这就是它三十年不倒的底气：说白了，门槛低到几乎没有——别的阵营还在装依赖、配环境，你的窗口已经弹出来了。注意最后一行的 mainloop()，它是这套代码里唯一的「玄学」：窗口明明死循环等着，界面却照样能点——这正是第 4.1 节讲的事件循环，本节末尾「跨阵营通用法则」还会回收这个伏笔。

阵营二：工业级重装备——PySide6 / PyQt6 与 Qt

Qt 是 1995 年从挪威起家的 C++ 跨平台框架，三十年攒下一身肌肉：WPS Office、VirtualBox、OBS Studio、Autodesk Maya 的界面都是它。Python 想借用这套肌肉，有两条官方通道：PyQt6（Riverbank 公司维护，GPL 或付费商业双授权）和 PySide6（Qt 官方亲维护，LGPL 授权更宽松，商用更省心）。两者 API 几乎是镜像的，教程互相通用——新人闭眼选 PySide6 即可。

它的立身本领是「正经应用」四个字全包：多窗口、菜单栏、状态栏、停靠面板、表格树形列表、多线程任务、数据库接口，工业软件需要的能力清单它几乎都打了勾。两件招牌工具尤其值钱：信号槽机制——界面事件和业务逻辑之间的对接头，比直接绑回调函数干净一个量级（它就是 Qt 版的事件系统，原理上与 § 4.2 讲的监听器同宗）；Qt Designer 拖拽设计器——控件拖进画布、对齐、保存成 .ui 文件，一行布局代码都不用写。

死穴是两个字：重。学习曲线陡——信号槽、布局管理器、模型/视图架构，每一层都要交学费；打包体积大，一个空窗口出来就是几十 MB；概念密度高，新手从 Tkinter 直接跳过来，常见「每行代码都懂、合起来不知道在干嘛」的失重感。它像一辆家用轿车：全能主力，但考驾照、养车、加油，样样都是成本。施工细节见 § 5.3。

同一个「点我改标题」的窗口，Qt 版长这样——行数多了些，但每一行都能对上一个正经概念：

from PySide6.QtWidgets import QApplication, QMainWindow, QPushButton

app = QApplication([])              # 第一个对象永远是「应用」本身
win = QMainWindow()                 # 主窗口
btn = QPushButton('点我', win)      # 按钮放进窗口
btn.clicked.connect(lambda: win.setWindowTitle('被点过了'))   # 信号接槽
win.show()                          # Qt 的窗口默认不显示，要喊一嗓子
app.exec()                          # 进入事件循环——§ 4.1 那口心脏

两段代码并排看，阵营间的「信息密度差」一目了然：Tkinter 版没有一个概念超出 Python 常识，Qt 版却塞进了应用对象、主窗口、信号槽、显式 show——多出来的每一行，都是为「正经软件」这个目标预付的成本。

阵营三：借浏览器当脸面——Streamlit / Gradio / NiceGUI

这一阵营的思路最讨巧：干脆不自己画界面，把画界面的活外包给浏览器。程序在你本地（或服务器）起一个小型 Web 服务，逻辑全在 Python 里跑，界面则是一个自动生成的网页——用户开个浏览器标签页就能用，手机、平板、别人的电脑，全都直接访问。这就是前面说的「外卖模式」：厨房还是你家厨房（Python 环境），菜却可以送到任何一间办公室。

三件代表产品各有侧重：Streamlit（2019 年）主打「脚本即应用」——你写一段顺序执行的 Python，它自动变成带按钮、滑块、图表的交互页面，每点一下就把脚本重跑一遍，数据科学圈的主力装备；Gradio 被 Hugging Face 收进门下，专做 AI 模型演示——上传图片、返回识别结果，十几行代码一个演示页，机器学习领域的标配；NiceGUI 则更接近「用 Python 写网页」，布局自由度最高，适合要长得像正经网站的内部系统。

它的甜蜜点是数据面板、AI 演示、内部看板：周五下午开始写，周一早上老板在浏览器里就能看。死穴也来自同一个设计：桌面感弱——它终究是个网页：离线使用别扭、窗口系统集成（系统托盘、全局快捷键）基本没有、复杂交互要绕着框架脾气走。想要「双击桌面图标、打开一个独立窗口」的正经软件感，还得看后面两个阵营。施工细节见 § 5.4。

它的体量同样夸张——一个带标题和折线图的页面，三行：

import streamlit as st
st.title('销售月报')
st.line_chart(月度数据)          # pandas 算好什么，页面就长什么样

命令行敲一句 streamlit run，浏览器自动弹出页面；把地址栏的链接发给同事，他手机点开就能看——不妨这样想：传统桌面软件是「请顾客来店里」，这一阵营是「中央厨房直接出餐」，界面根本不归你管，你只管把菜（数据）做好。

阵营四：背一个浏览器的桌面应用——Electron 与 Tauri

2013 年，GitHub 团队给自己的代码编辑器 Atom 找出路，想出了界面开发史上最豪横的一招：干脆把整个 Chromium 浏览器打进安装包里，界面用 HTML/CSS/JavaScript 写，本地能力用 Node.js 补——这就是 Electron。此后十年它攻城略地：VS Code、Slack、Discord、飞书桌面版，一大票你天天在用的软件都是它。立身本领一句话：整个前端生态随便用——npm 上百万个包、成熟的组件库、你已会的每一分前端手艺，原封不动搬进桌面软件。

豪横的代价也直白：每个 Electron 应用都背着一整个浏览器。安装包 100MB 起步，开三个 Electron 应用就等于同时开了三个 Chromium——内存大户名副其实，程序员圈里「不环保应用」的梗说的就是它。

Tauri（2022 年出 1.0）是针对这个软肋的正面回答：浏览器内核不带了，用操作系统自带的 WebView（Windows 上是 WebView2，macOS 上是 WKWebView），后端换成以省内存著称的 Rust。安装包从 100MB 级掉到几 MB 级，内存占用砍掉一大截。代价是两笔：各系统的 WebView 内核并不完全一致，兼容性要自己多留心；后端逻辑要碰 Rust，学习曲线是道真实的门槛。想象一下两种搬家方式：Electron 是把整套房连家具带厨房全搬来——换个城市也过得跟原来一模一样，就是搬家公司账单吓人；Tauri 是轻装上路，借房东现成的厨卫——又快又省，代价是每家房东的灶台脾气略有不同（各系统 WebView 内核差异）。施工细节见 § 5.5。

阵营五：操作系统的亲儿子——Win32 与 .NET 系

最老的一条路，也是最根上的一条路：Win32 API，1995 年随 Windows 95 定型，C/C++ 语言直接调用。你在第 4 章事件循环里学过的那套「取消息—分发—处理」的循环，就是从 Win32 的消息循环一脉相承下来的——所有 Windows 界面框架的底下，坐着的都是它。今天手写 Win32 的人不多（产量低、样板代码多），但系统自带的小工具、安全软件的驱动级界面里它仍在服役——好比手排挡老式机械：一般人开不动，工匠拿它做极致可控的活。

更多的人走的是微软在上面盖的四层楼：WinForms（2002 年，拖控件的最快出活路线，内部封装的就是 Win32）；WPF（2006 年，XAML 界面描述 + 数据绑定 + DirectX 硬件加速，Windows 桌面应用的经典重炮）；WinUI 3（2021 年，微软当代主推的现代化 Fluent 界面）；以及跨平台的 MAUI。这条线一门 C# 语言通吃，性能和原生脸面都是亲儿子级待遇。

阵营里还有一位非微软编制的猛将：Avalonia——C# 写的跨平台 XAML 框架，一套代码跑 Win/macOS/Linux/移动端，控件全部自绘（Skia 渲染）不依赖系统，堪称「WPF 的跨平台精神续作」，在国外桌面工具圈相当活跃。这条阵营的死穴就一条：出了 Windows，WinForms/WPF/WinUI 们立刻水土不服——想跨平台，要么 Avalonia，要么 MAUI，要么换阵营。施工细节见 § 5.5。

一张决策树：五问走到答案

地图认完了，把五个问题串成一棵树。决策树的用法像医院分诊台：从第一问进，每一层回答都把你引向下一问或直接送到答案，答到底，答案自己浮出来。医院分诊台其实就是这棵树的原型：护士从不问你「你喜欢哪个科室」，只问「哪里不舒服」——问题永远顺着病情走，不顺着科室名气走；选型同理，问题顺着需求走，不顺着框架热度走：

层次问题答案 A 走向答案 B 走向
第 1 层要联网或多端访问吗？要 → 直接去阵营③（B/S 路线）不要 → 进第 2 层

地图上的孤勇者：Flet、Dear PyGui 与 Avalonia

主流五阵营之外，地图边缘还有几位路线独特的选手。把它们画进地图，不是为了赶时髦，而是它们各自代表一种「换一条轴」的解题思路，某天你的需求恰好落在那条轴上，它们就是唯一解。

Flet（2022 年）：Python 直接写 Flutter 界面。Flutter 是 Google 那套自绘 UI 引擎（Material Design 外观），本来要用 Dart 语言写；Flet 在中间架了桥，让你用纯 Python 就能拿到那副现代、顺滑、跟手机一个审美的界面，而且同一份代码能编译成手机 App——「Python 写一次、电脑手机都能跑」是它的独门卖点，适合既想快速出活又想多端的 Python 人。

Dear PyGui：GPU 即时模式渲染——其实就是把第 2 章渲染管线里讲的那些显卡本事，直接借来画界面。它不走「框架养一棵控件树」的保留模式，而是每一帧由你的代码亲手把整个界面重新画一遍（即时模式）。好处是实时刷新快得惊人、上万数据点不眨眼，游戏调试工具、工程实时监视面板这类「每秒都在变」的场景是它的主场；代价是外观自成一路、不像任何系统的亲儿子，表单类常规应用反而不占便宜。

Avalonia 前面提过，单独再点名一次是因为它在地图上位置微妙：论血缘它属于 .NET 阵营，论跨平台哲学它更像 Qt（自绘、不依赖系统控件），论语言生态又是 C# 独享。「C# 出身、要跨平台、嫌 MAUI 不够稳」——满足这三条的人，地图上就剩它一个答案。三位孤勇者共同的启示：边缘选项不是给追新的人准备的，是给需求恰好特殊的人准备的——需求不特殊，就别为它们绕路。

选型三大陷阱：追新、大炮打蚊子、以框架学编程

地图和树都给了，最后讲三个反复坑人的陷阱——它们坑的不是知识，是心态。

陷阱一：追新。GitHub 上星标涨得快、社区里讨论度高的新框架总显得格外性感，但框架成熟的标志从来不是新，而是「你将遇到的每个坑，都有人提前踩过并写了帖子」。新框架文档不全、API 三个月一变、搜报错搜不到答案——这些隐性成本不会出现在任何对比表里。判断方法很土但有效：把你打算写的第一段代码遇到的第一个报错，原样丢进搜索引擎——能搜出三条以上有效答案的框架，才值得新手入场。

陷阱二：大炮打蚊子。给同事做个查库存的小窗口，上了 Electron：安装包 150MB，同事电脑开一个窗占半 G 内存，你还得研究怎么打包更新。杀鸡用了航母，鸡没杀死，先把港口修炸了。自检口诀：受众是自己和小圈子、界面是表单级、三天内要交差——三条中两条，你就该在阵营①③里选，别往下看。

陷阱三：以框架学编程。「我想学 PySide6，帮我找个项目练手」——这句话的语序就是病根。通俗地说，它把因果讲反了：工具成了目的，项目成了手段，本末倒置。正确的顺序永远是「我想做 X，X 需要界面，所以学某个框架」。为了学而找的项目，通常撑不过三周热情；为了做而学的框架，每个知识点都有地方安放。学海无涯，但求学的方法论不能是「先买那套 108 件德国工具，再琢磨修什么」。

选错了怎么办：迁移成本与沉没成本

就算五问都答对了，选错仍然可能发生——需求会变、认知会变。这时候要算的账只有一本：迁移成本，而决定这本账厚薄的，是你当初有没有把业务逻辑和界面代码分开写。

界面层的代码——布局、控件、事件绑定——换个框架基本全部作废，这没得救；但真正的核心资产是界面底下那层业务逻辑：解析文件的函数、算数的引擎、访问数据库的代码。当初若把它们老老实实写成不依赖任何框架的独立模块，换框架就只是「换皮不换芯」：Tkinter 的皮换成 PySide6 的皮，芯原样搬过去。反过来，如果当年图省事把逻辑写死在按钮的回调函数里，那换框架就是连根重写。这就是选型之外最重要的架构保险：皮和芯永远分开放。落到工程上，它就是文件夹里两个互不打扰的模块：

my_tool/
├── core/              # 芯：纯业务逻辑，一行界面代码都不 import
│   ├── parse.py       #   解析文件、算数、读写数据库……
│   └── calc.py        #   这些函数换个框架照样能用
└── ui/                # 皮：只管摆控件、转发事件
    └── main.py        #   import core，按钮一点就调用它

验收标准只有一条：把 ui 文件夹整个删掉，core 里的代码照样能跑、能被单元测试直接调用——满足这一条，将来无论换哪张皮，芯都原封不动。打个比方，这就是餐厅的「后厨与餐厅分离」：装修可以翻新，菜谱和厨师不必动。

关于沉没成本只提醒一句：「我已经学了三周了」不是继续走错的理由，三周沉没对比半年错路，止损永远划算。但换之前先做痛感评估：能忍（只是不顺手）→ 继续做完；真痛（需求撞上框架死穴）→ 尽早换；已经崩（做一半发现走不通）→ 先停下来画清楚需求再动，别在慌乱中跳进第二个错误选择。

三类人的三张答案卷：课设、看板、独立产品

方法讲完，给三张已经答完的卷子做参照。这三张卷子相当于三种最常见的身份，每一张都完整走过一遍五问，你可以把自己的答案对进去：

大学生做课程设计。需求：两周内交、答辩现场要能跑、评委看功能不看框架、自己电脑开发自己电脑演示。答案：Tkinter。理由极其现实：环境零风险（标准库自带，答辩教室的电脑装个 Python 就能跑）、不可能因为依赖问题当场翻车。课设的本质是一场考试，考试的第一原则不是漂亮，是不出事故。想要现代观感再套一层 CustomTkinter。

数据分析师周一要汇报。需求：周五下午才拿到数据，周一早上给全部门看图表，同事们电脑里什么都没装，有人要用手机看。答案：Streamlit（阵营③）。理由：pandas 画好的图直接进页面、免安装发链接即看、手机浏览器天然兼容——为一次汇报去学 Qt 的信号槽，是把杀鸡的时间花在了磨航母上。

独立开发者做正经产品。需求：要发布给陌生用户、双击安装、体积体面、支持自动更新、未来可能上多平台。答案：先按语言分流——Python 出身选 PySide6（生态成熟、打包链路齐全）；前端出身选 Electron（快速）或 Tauri（体面）；C# 出身选 Avalonia。且无论选谁，§ 5.6 的打包、签名、自动更新三关都必须提前规划——独立产品死于「做完了却发不出去」的，远多于死于功能不足的。

跨阵营通用法则：无论选谁，这四件事都一样

地图分了五大阵营，但它们地底下埋着同一套地基。这也是整个界面篇最划算的一笔账：你在第 1 到 4 章辛苦学的原理，一条都不会浪费——换个框架只是换语法，思路原样继承。

法则一：每个框架地下都埋着同一个事件循环。Tkinter 叫 mainloop()，Qt 叫 app.exec()，Win32 里是 GetMessage 消息循环，浏览器里叫 event loop（§ 4.1）——名字不同，干的活儿一模一样：等事件、取事件、分发、处理，无限循环。由它直接推出一条铁律：耗时操作永远别写在按钮的回调里——循环被重活堵住，界面就「未响应」。每个阵营都备有各自的后台线程方案，治的是同一种病。

法则二：布局永远是那三种思路。绝对定位（坐标写死）、流式（一个挨一个排）、网格（按行列摆）——第 3 章在网页里学的三套布局哲学，在 Tkinter 的 place/pack/grid、Qt 的布局管理器、WPF 的面板系统里全部原样重逢。学一次，用到哪都在。

法则三：保留模式框架都养着一棵树。浏览器养 DOM，Qt 养 QObject 树，WPF 养可视树——树上的事件查找、父子关系、命中定位，原理与 § 4.2 讲的 e.target 和冒泡完全同宗；而即时模式的 Dear PyGui 没有树，因为界面每帧重画。有没有这棵树，正是两大模式的分界线。

法则四：所有框架画的都是同一批标准件。按钮、输入框、下拉框、列表、对话框——第 1 章讲过，这套「控件词汇表」是几十年沉淀下来的通用语，各框架只是口音不同。标准件不够用、要自绘时，每个阵营都明码标价收「定制费」：越底层的框架自由度越高、工时也越贵。这四条法则就是选型的定心丸：地图上五条路条条通山顶，因为山只有一座。

把五大技术栈想成「出门选交通工具」
出门第一件事从来不是选车，是想清楚去哪、带谁、赶不赶时间——这就是本节的五问。然后才轮到挑车：

Tkinter 是步行加共享单车——零成本随取随用，楼下买瓶酱油它最快；你要骑着它去外地，是自己选错了。

CustomTkinter 是电动车——还是那双腿（同一套 API），代步体验升级一截，行程半径没变。

PySide6 是家用轿车——全能主力，近可买菜远可自驾；代价是要考驾照（学习曲线）、要养车（体积与复杂度）。

阵营③（Streamlit 们）是外卖——厨房在你家电脑，菜能送到任何人的手机；但你永远失去了「坐在店里」的桌面感。

Electron 是房车——卧室厨房浴室全带上（整个 Chromium），走到哪住到哪；费油、占地，光启动就够喝一壶。

Tauri 是轻装折叠车——借房东家的厨卫（系统 WebView），自己只带行李，又快又省；代价是每家装潢略有不同，要留心兼容。

Win32 是手排挡老式机械——工匠专属，别人开不动，开得动的人能榨出极致控制力。

.NET / Avalonia 是厂商正规车队——Windows 大道上是嫡系待遇，Avalonia 还能开出省（跨平台）。

交通工具没有最好，只有最合适——先看你去哪（需求），再看开什么（工具）。反过来选，再贵的车也只是堵在错的路上的铁盒子。

本节回顾：一张地图，五个问题，一条纪律

本节没有教你写一行界面代码，但它交付的可能是整个第 5 章最值钱的东西：一张按「你要做什么」分区的地图，和一套把需求翻译成技术条件的五问。受众决定成本档位，联网与否决定架构路线，语言熟练度决定阵营归属，复杂度和体积敏感度完成最后收口。五大阵营各自的人设——Tkinter 的零成本、Qt 的工业全包、浏览器阵营的外卖模式、Electron/Tauri 的网页手艺移植、.NET 系的原生嫡系——加上 Flet、Dear PyGui、Avalonia 三位孤勇者，合起来就是当今桌面界面开发的完整版图。而四条跨阵营通用法则——同一个事件循环、同三种布局思路、同一棵控件树、同一批标准件——保证了这张地图上任何一条路，都通向你已经在第 1–4 章爬过的那座原理之山。

而压在所有方法之上的只有一条纪律：先有活，后有工具。接下来五节按地图顺序逐阵营进施工：§ 5.2 从 Tkinter 的十分钟小工具起步，§ 5.3 驾驭 Qt 的工业重装备，§ 5.4 借浏览器做数据面板，§ 5.5 打通网页技术与原生路线，最后 § 5.6 学会让别人双击就能用。选型是地图，施工是行军——地图看完了，该上路了。
